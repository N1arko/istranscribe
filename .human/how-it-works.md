# Как работает spec-driven workflow

Проект разделяет канон, конкретную работу и память сессии.

| Сущность | Роль |
|---|---|
| `SPEC-MAP.md` | Каталог спек, их responsibility и lifecycle. |
| `PROP`, `FEAT`, `INFRA` | Долговечный канон поведения, контрактов и операций. |
| `WI-NNN` | Один ограниченный outcome, scope, acceptance и Result. |
| `BOARD.md` | Статус, owner, priority и blocker WI. |
| `WAL.md` | Checkpoint незавершённой работы. |
| `TECHDEBT.md` | Долгоживущие инженерные компромиссы. |

Одна спека может реализовываться несколькими WI. Один WI может использовать несколько точных `spec://...#anchor`, если результат один и проверяется вместе.

## Обычный процесс

1. Найти owning spec через `SPEC-MAP`, `structure.md` и `@spec`.
2. Обновить канон, если поменялось поведение или обнаружен реальный пробел.
3. Создать WI при самостоятельном scope, риске, зависимости или продолжении между сессиями.
4. Добавить одну строку WI в BOARD.
5. Выполнить acceptance.
6. При остановке сохранить короткий WAL checkpoint.
7. При завершении заполнить Result, архивировать WI и переместить строку в Done.

Одношаговая работа с очевидной owning spec завершается в текущей сессии без WI, BOARD и WAL.

`PROP`, `FEAT` и `INFRA` используют lifecycle `draft`, `active`, `superseded`, `retired`. Старые IDs и `spec://` пути сохраняются. Новый самостоятельный канон получает новый ID; повторный проход реализации получает новый WI.

AI начинает с `AGENTS.md` и `specs/protocols/BOOT.md`. Новый или существенно изменённый spec-owned код получает `@spec` на точках ответственности.
