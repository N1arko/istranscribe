# Техническое задание
## Windows-приложение для автоматической фиксации встреч, записи аудио и транскрибации

**Версия документа:** 1.1  
**Дата:** 2026-04-02  
**Статус:** базовое ТЗ на MVP с заделом под развитие

---

## 1. Назначение продукта

Разработать настольное приложение для Windows, которое автоматически или полуавтоматически фиксирует встречи и звонки пользователя, записывает выбранные источники аудио, сохраняет записи на диск и создаёт текстовую транскрибацию на основе Fireworks Whisper.

Приложение должно закрывать задачу **автофиксации встреч без ручной рутины** и быть пригодным для ежедневного использования как личный инструмент.

Ключевая идея продукта:
- приложение работает в фоне;
- понимает, когда вероятно началась встреча;
- по настройкам либо автоматически пишет, либо спрашивает подтверждение;
- сохраняет аудио локально;
- отправляет запись в Fireworks на транскрибацию;
- сохраняет результат на диск в `.md`;
- позволяет быстро найти и открыть нужную встречу.

## 2. Цели MVP

### 2.1. Что должно уметь приложение в MVP

1. Работать как tray-приложение в Windows.
2. Следить за whitelisted приложениями и их аудиоактивностью.
3. Начинать запись по правилам автоматики или по ручной команде.
4. Поддерживать режим подтверждения: «Слышу — записываю?».
5. Записывать:
   - выходной звук выбранного процесса **или** выбранного output device;
   - микрофон;
   - оба источника одновременно.
6. Сохранять аудиофайлы локально в указанную папку.
7. Отправлять завершённые записи в Fireworks для транскрибации.
8. Поддерживать diarization при транскрибации.
9. Сохранять транскрибацию на диск в формате Markdown.
10. Иметь базовый список записей/встреч внутри приложения.
11. Позволять переотправить неудачную транскрибацию.
12. Хранить пользовательские настройки, включая API key Fireworks.

### 2.2. Что в MVP не входит

1. Командная работа.
2. Серверная часть и аккаунты пользователей.
3. Биллинг, лимиты, подписки.
4. CRM-интеграции.
5. OpenRouter/LLM-оценка содержания встречи.
6. Семантический поиск по смыслам.
7. Редактор транскриптов внутри приложения.
8. Синхронизация между устройствами.
9. macOS / Linux версии.

## 3. Целевая платформа и ограничения

### 3.1. Поддерживаемая платформа

Основная платформа MVP:
- **Windows 11**;
- **Windows 10 build 20348+**.

### 3.2. Причина ограничения

Для корректного захвата аудио **конкретного процесса и его дочерних процессов** используется process loopback capture на базе Windows Core Audio / WASAPI. Этот режим доступен начиная с Windows 10 build 20348. На более старых версиях Windows допускается только деградированный режим через system loopback по устройству. Источники Microsoft это прямо фиксируют.  

### 3.3. Поведение на неподдерживаемых системах

Если ОС не поддерживает process loopback:
- приложение должно работать;
- режим **Auto с process capture** должен быть недоступен;
- пользователь может использовать:
  - запись по device loopback;
  - запись микрофона;
  - ручной режим Force Record.

## 4. Пользовательский сценарий

### 4.1. Базовый сценарий

1. Пользователь устанавливает приложение.
2. При первом запуске выбирает:
   - папку для аудиозаписей;
   - папку для транскрибаций;
   - output device;
   - microphone device;
   - список приложений, за которыми нужно следить;
   - режим работы: Off / Ask / Auto.
3. Приложение работает в фоне.
4. Когда whitelisted приложение начинает воспроизводить звук, приложение:
   - либо само начинает запись;
   - либо показывает запрос подтверждения;
   - либо ничего не делает, если выбран режим Off.
5. После завершения встречи запись закрывается и сохраняется на диск.
6. Файл уходит в очередь транскрибации.
7. После обработки создаётся `.md`-файл с транскриптом.
8. Пользователь открывает нужную встречу из списка или напрямую из папки.

### 4.2. Ручной сценарий

1. Пользователь нажимает горячую клавишу или кнопку Force Record.
2. Приложение начинает писать выбранные устройства, игнорируя автоусловия.
3. Пользователь вручную останавливает запись.
4. Далее запись проходит тот же пайплайн сохранения и транскрибации.

## 5. Режимы работы

### 5.1. Off

Автоматическая фиксация отключена. Приложение не запускает запись самостоятельно.

Разрешено:
- ручной запуск записи;
- просмотр списка встреч;
- запуск транскрибации уже сохранённых файлов.

### 5.2. Ask

При обнаружении вероятной встречи приложение предлагает начать запись.

Особенности:
- до подтверждения используется **prebuffer**;
- если пользователь нажимает «Да», в итоговую запись включается prebuffer;
- если пользователь нажимает «Нет», prebuffer сбрасывается;
- если пользователь игнорирует окно, поведение определяется настройкой таймаута.

### 5.3. Auto

Приложение автоматически запускает запись при выполнении условий триггера.

### 5.4. Privacy Pause

Временная принудительная пауза поверх любого режима.

Во время активного Privacy Pause:
- запись не начинается автоматически;
- текущая запись ставится на паузу или завершается в зависимости от настройки;
- в UI должно быть явно видно, что приватный режим активен.

### 5.5. Force Record

Ручной режим записи по команде пользователя.

В MVP Force Record должен писать:
- выбранный output device;
- выбранный microphone device;
- оба источника одновременно по настройке.

Force Record не зависит от whitelist процессов.

## 6. Логика определения начала встречи

### 6.1. Источники сигнала для определения старта

Приложение должно использовать комбинацию признаков:

1. Запущен whitelisted процесс.
2. У процесса есть активная аудиосессия.
3. Аудиоуровень выше заданного порога в течение заданного времени.
4. Для браузеров — совпадает имя whitelisted процесса, даже если содержимое идёт из его process tree.

### 6.2. Условия старта в режиме Auto

Запись стартует, если одновременно выполнены условия:
- обнаружен whitelisted процесс;
- аудиосессия процесса перешла в состояние `Active`;
- уровень аудио держится выше порога не менее `N` секунд.

Начальные значения по умолчанию:
- порог тишины: настраиваемый, в MVP в процентах/условных единицах;
- минимальная длительность сигнала до старта: **2 секунды**.

### 6.3. Условия старта в режиме Ask

При тех же условиях, что и в Auto:
- показывается диалог/тост «Слышу встречу — записывать?»;
- в фоне уже заполняется prebuffer.

### 6.4. Что не должно считаться встречей по умолчанию

1. Одиночные системные звуки.
2. Короткие уведомления длительностью ниже порога запуска.
3. Шумы микрофона без активности whitelisted процесса — если пользователь не включал запись микрофона вручную.

### 6.5. Автообнаружение новых аудиоактивных приложений

Если включена опция автообнаружения новых аудиоактивных приложений, приложение должно отслеживать процессы, которые:
- не находятся в whitelist;
- создают аудиосессию воспроизведения;
- держат аудиоактивность выше порога не менее `N` секунд.

Далее применяется одна из политик:
1. **Автоматически добавлять в whitelist** — процесс добавляется в whitelist автоматически.
2. **Предлагать добавить в whitelist** — пользователю показывается уведомление/диалог с предложением добавить процесс в whitelist.
3. **Отключено** — новые процессы не предлагаются и не добавляются автоматически.

Дополнительные требования:
- системные процессы, служебные процессы Windows и заранее заданные исключения не должны автоматически добавляться в whitelist;
- при автоматическом добавлении должно фиксироваться событие в логах;
- пользователь должен иметь возможность удалить автоматически добавленное правило.

## 7. Логика завершения записи

### 7.1. Автоматическое завершение

Текущая запись завершается, если выполнено одно из условий:
- whitelisted процесс завершён;
- аудиосессия процесса неактивна дольше `M` секунд;
- пользователь нажал Stop;
- пользователь активировал режим «завершать при Privacy Pause».

Значение по умолчанию:
- задержка перед остановкой: **20 секунд**.

### 7.2. Склейка пауз

Если после периода тишины активность вернулась раньше, чем истёк лимит остановки, запись должна продолжаться в рамках той же сессии.

### 7.3. Защита от дробления одной встречи

Не создавать новую встречу, если:
- тот же источник активировался повторно в течение малого окна времени;
- пользователь не останавливал запись вручную.

Рекомендуемое начальное окно склейки: **60 секунд**.

## 8. Источники аудио

### 8.1. Поддерживаемые источники

Приложение должно поддерживать следующие типы аудиоисточников:

1. **Process output capture** — захват output-а конкретного процесса и его дочерних процессов.
2. **Device loopback capture** — захват всего звука выбранного output device.
3. **Microphone capture** — захват выбранного микрофона.

### 8.2. Поведение по умолчанию

#### Для режима Auto
По умолчанию использовать:
- `process output + microphone`.

#### Для режима Force Record
По умолчанию использовать:
- `selected output device + microphone`.

### 8.3. Настройки источников

Пользователь должен иметь возможность выбрать:
- писать только output;
- писать только microphone;
- писать оба источника.

### 8.4. Раздельное хранение дорожек

В MVP рекомендуется хранить:
- отдельный raw-файл output-дорожки;
- отдельный raw-файл microphone-дорожки;
- при необходимости объединённый микс для отправки в транскрибацию.

Это нужно для:
- большей надёжности;
- будущего улучшения обработки;
- возможности отладки качества захвата.

## 9. Prebuffer

### 9.1. Назначение

Prebuffer нужен для режима Ask, чтобы не терять первые секунды встречи.

### 9.2. Требования

1. Приложение должно хранить кольцевой буфер последних секунд аудио.
2. Буфер ведётся только для разрешённых источников.
3. Буфер не должен сохраняться на диск без подтверждения, если пользователь выбрал Ask.

### 9.3. Значение по умолчанию

- длительность prebuffer: **15 секунд**.

### 9.4. Настройка

Пользователь может задать:
- 5 сек;
- 10 сек;
- 15 сек;
- 30 сек.

   - спросить пользователя, если это возможно без потери записи.

   - автоматически добавлять в whitelist;

## 14. Пайплайн записи

### 14.1. Этап 1. Detection

Сервисы наблюдают за:
- процессами;
- аудиосессиями;
- устройствами;
- уровнем сигнала.

### 14.2. Этап 2. Session bootstrap

Если условия выполнены:
- создаётся объект MeetingSession;
- поднимаются нужные capture pipelines;
- начинается запись во временные файлы.

### 14.3. Этап 3. Recording

Во время записи:
- идёт захват источников;
- обновляется статус в UI;
- пишутся временные чанки или непрерывный поток;
- считаются длительность и метаданные.

### 14.4. Этап 4. Finalize

При остановке:
- потоки аккуратно закрываются;
- временные файлы переименовываются в финальные;
- рассчитывается итоговая длительность;
- сессия уходит в очередь транскрибации.

### 14.5. Этап 5. Transcription

Worker берёт завершённую сессию и:
- формирует файл или микс;
- отправляет его в Fireworks;
- получает результат;
- сохраняет JSON и Markdown.

## 15. Пайплайн транскрибации

### 15.1. Базовый режим

После завершения записи приложение должно запускать pre-recorded transcription через Fireworks API.

### 15.2. Требования к API-части

Приложение должно уметь передавать:
- файл аудио;
- модель;
- язык при необходимости;
- diarization settings;
- формат ответа.

### 15.3. Форматы ответа

Минимум сохранять:
- текстовую транскрибацию;
- полный `verbose_json`, если включена diarization.

### 15.4. Diarization

Если diarization включена:
- приложение должно отправлять корректные параметры запроса;
- сохранять разметку спикеров;
- по возможности отражать спикеров в `.md`.

### 15.5. Повторные попытки

Если Fireworks недоступен или возвращает ошибку:
- статус меняется на `failed`;
- пользователь может нажать Retry;
- при включённой опции выполняются автоматические повторы.

Значения по умолчанию:
- количество повторов: **3**;
- интервалы: **1 мин / 5 мин / 15 мин**.

## 16. Формат Markdown-транскрибации

### 16.1. Общие требования

Каждая завершённая транскрибация должна сохраняться в отдельный `.md`-файл.

### 16.2. Рекомендуемая структура файла

```md
# Название встречи

- Дата: 2026-04-02
- Время начала: 15:41:12
- Время окончания: 16:23:49
- Длительность: 42м 37с
- Источник: Zoom.exe
- Режим записи: auto
- Output device: Headphones (USB)
- Microphone: Shure MV7
- Diarization: on

## Транскрипт

[Speaker 1 | 00:00:02]
Добрый день, давайте начинать.

[Speaker 2 | 00:00:05]
Да, вижу вас, слышу.
```

### 16.3. Название файла

Шаблон по умолчанию:

`YYYY-MM-DD HH-mm — SourceApp — SessionId.md`

Пример:

`2026-04-02 15-41 — Zoom — a1b2c3.md`

### 16.4. Дополнительные файлы

Рядом с `.md` при необходимости сохраняются:
- `*.json` — полный ответ Fireworks;
- `*.wav` / `*.m4a` — исходная запись;
- `*.log` — опционально, если сессия завершилась ошибкой.

## 18. Работа с устройствами

### 18.1. Требования

Приложение должно:
- перечислять активные output devices;
- перечислять активные microphone devices;
- уметь подхватывать системный default device;
- реагировать на изменение default device;
- при включённой опции автоматически обнаруживать появление новых output devices;
- при включённой опции автоматически обнаруживать актуальный microphone device.

### 18.2. Автоматическое обнаружение устройств воспроизведения

Если включена опция «Автоматически обнаруживать устройства воспроизведения», приложение должно:
- отслеживать подключение новых output devices;
- обновлять список доступных устройств без перезапуска приложения;
- при необходимости переключаться на новый default output device по политике настроек;
- логировать факт появления нового устройства и принятое решение.

### 18.3. Автоматическое обнаружение микрофона

Если включена опция «Автоматически обнаруживать микрофон», приложение должно:
- отслеживать появление, исчезновение и смену активного microphone device;
- уметь переключаться на актуальный микрофон без необходимости ручного входа в настройки;
- не допускать ситуации, в которой встреча продолжается без записи микрофона только из-за смены гарнитуры или подключения нового устройства, если это можно предотвратить настройками;
- логировать факт переключения микрофона и выбранное правило.

### 18.4. Сценарий смены устройства во время записи

Если во время активной записи устройство пропало или изменилось:
- приложение не должно падать;
- текущая сессия должна либо корректно завершиться, либо продолжиться по правилам настройки;
- при включённом автообнаружении микрофона должен применяться сценарий переключения на новый доступный вход;
- событие должно попасть в лог.

### 18.5. Сценарий подключения/отключения устройств

При изменении списка устройств:
- список в UI должен обновляться;
- пользователь должен видеть актуальные названия устройств;
- привязка по device ID должна сохраняться, если устройство вернулось;
- если устройство появилось во время записи, должно применяться правило автообнаружения или переключения из настроек.

## 28. Технические основания и внешние зависимости

Ниже — ключевые технические факты, на которые опирается архитектура:

1. **Windows process loopback capture** позволяет ограничить захват аудио указанным процессом и его дочерними процессами; для этого используется `AUDIOCLIENT_PROCESS_LOOPBACK_PARAMS`, а минимум по версии клиента — Windows 10 build 20348.  
2. **System loopback capture** в WASAPI пишет звук, который проигрывается на rendering endpoint device, то есть весь системный микс выбранного устройства.  
3. **Audio sessions** в Windows имеют состояния `Active`, `Inactive`, `Expired`, и это подходит для логики автостарта/автоостановки.  
4. **MMDevice API** позволяет перечислять audio endpoint devices и подписываться на изменения устройств и default endpoint.  
5. **DPAPI / ProtectedData** подходит для локального хранения API key на Windows.  
6. **Fireworks audio transcription API** поддерживает diarization; для неё требуется `response_format=verbose_json` и `timestamp_granularities` с `word`.  
7. **Fireworks transcription** возвращает не Markdown, поэтому `.md` должен собираться локально приложением из ответа API.
