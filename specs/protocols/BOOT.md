# BOOT

Этот файл читается в начале каждой AI-сессии.

## 1. Быстрый вход {#entry}

Сначала разреши рабочий контекст минимальным числом чтений.

### Если в запросе указан `WI-NNN`

1. Открой его файл в `specs/work/` или `specs/work/archive/`.
2. Найди одну строку WI в `specs/BOARD.md`.
3. Ищи checkpoint этого WI в `specs/WAL.md`. Открывай WAL целиком только при наличии релевантной секции или общего решения.
4. Открой перечисленные в WI governing specs и только необходимые constraint/affected specs.

### Если WI не указан

Ищи контекст в таком порядке:
1. активные строки `BOARD.md`;
2. человекочитаемая карта `SPEC-MAP.md`;
3. техническая карта `common/structure.md`;
4. имена файлов, заголовки и anchors в `specs/**`;
5. `@spec` в коде и тестах;
6. названия модулей, экранов, процессов, компонентов и файлов.

Поиск выполняется лениво. Не загружай весь spec-space и весь код, если задача уже разрешилась меньшим контекстом.

`specs/.me` нужен перед claim work item или изменением ownership, `BOARD.md` и `WAL.md`. Для read-only анализа и одношаговой работы без операционного учёта отсутствие `.me` не блокирует чтение. Не коммить `specs/.me`.

## 2. Выбор контура {#scope}

- Одношаговая работа: завершается в текущей сессии по очевидной owning spec. WI, BOARD и WAL не создаются.
- Существующий work item: работай по найденному `WI-NNN`; WAL меняй только при checkpoint.
- Новая отслеживаемая работа: создай WI по `WORK-ITEM-PROTOCOL.md`, добавь одну строку в BOARD и создай WAL только при незавершённости или handoff.
- Новый или изменяемый канон: следуй `SPEC-AUTHORING-PROTOCOL.md`, зарегистрируй спеку в `SPEC-MAP.md`, обнови `structure.md` только при смене topology.

## 3. Маршрутизация {#routing}

- Создание или глубокая переработка спеки: `SPEC-AUTHORING-PROTOCOL.md`.
- Lifecycle, direct edit, supersession или конфликт со спекой: `SPEC-PROTOCOL.md`.
- Создание, разбиение, исправление или завершение WI: `WORK-ITEM-PROTOCOL.md`.
- Статус, owner, priority или blocker: `BOARD-PROTOCOL.md`.
- Checkpoint, handoff или возобновление: `WAL-PROTOCOL.md`.
- Сознательный компромисс вне scope: `TECHDEBT-PROTOCOL.md`.
- Внедрение workflow в существующий проект: `.human/adopt-existing-project-agent.md`.

## 4. Основные правила {#rules}

- Код, противоречащий ясной активной спеке, исправляется по канону. Для отслеживаемого исправления используй `Kind: fix`, `Canon action: none`.
- Изменение поведения проходит через direct edit или supersession по `SPEC-PROTOCOL.md`.
- Новый или существенно изменённый spec-owned код получает полный `@spec spec://...#...` на точках ответственности.
- Спорное место помечай `REVIEW`. Высокий риск для данных, безопасности, денег или основного сценария требует решения человека.

## 5. Завершение {#finish}

- Завершённый WI: пройди acceptance, заполни Result, архивируй WI, переведи BOARD в Done и удали его checkpoint WAL.
- Незавершённый WI: сохрани статус и один короткий WAL-checkpoint с ближайшим шагом.
- Одношаговая работа: сообщи изменённые файлы и проверки; операционный слой не меняй.
